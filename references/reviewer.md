# Reviewer Mode

基于原需求、设计和最终代码找具体问题。`--review` 默认只读，不改业务代码或设计文件；用户授权修复，或当前是
完整开发任务的收尾阶段时，才进入修复闭环。模式切换不等于调用一个已安装的命令行程序。

## 1. 确定输入与完整范围

读取项目指令、原需求、设计及其 AC、当前源文件、相关调用方与测试。设计本身也可被质疑。
记录 review 的分支、HEAD、基线来源与工作区状态；不要凭空假定基线总是 main。

```sh
git status --short
git diff --stat
git diff
git diff --cached
git ls-files --others --exclude-standard
```

以上仅覆盖未提交变更。有功能分支已提交变更时，从 PR / 用户指定目标分支 / 仓库事实确定
基线，用 `git merge-base <base> HEAD` 记录 merge-base，再查看
`git diff <merge-base> HEAD`。把分支提交、staged、unstaged 与未跟踪文件合并为审阅清单。
读取相关未跟踪文件的真实内容；普通 `git diff` 不包含它们。不要把状态中用户原有改动算作自己修改。
重命名、删除、配置、迁移、生成物和锁文件都按实际影响检查，不只读核心源文件。

新仓库没有 HEAD 时，明确写“初始文件集”，逐项审查文件；不要运行依赖有效 HEAD 的命令并
将失败解释成无变更。没有 Git 时使用工具可验证的文件比较，明确覆盖限制。
只提供局部 diff 时只能出具局部结论；不能因局部未见问题推断完整功能可 Done。

缺少事前设计时如实记录缺口。review-only 请求仍可审查已有代码，但不能声称符合未见过的设计。
完整开发任务可补建标明“追溯设计”的记录，由原需求和代码事实推导；重新核对验收，不能伪造批准历史。

## 2. 优先查有后果的问题

- AC 是否真正实现；正常、失败、并发和兼容路径是否符合契约。
- 职责是否混合；模块边界与依赖方向是否被破坏；SQL、框架或第三方协议是否无意泄漏到业务层。
- 条件分支增加是否造成多个修改点或不一致行为；不要仅因存在 if / switch 就报告问题。
- 隐藏副作用、错误吞没、授权遗漏、状态同步、数据完整性与重试是否带来实际风险。
- 新接口、wrapper、manager、factory、继承或抽象是否降低可理解性；能否删除且保留需求。
- 测试能否证明关键行为，还是只重复实现；测试是否需要不必要的外部设施。
- 实际新增/修改/删除文件与预算相比是否有未解释的范围扩张；是否混入无关清理。

没有可定位的触发条件、影响或证据时，不把个人风格偏好升级成缺陷。
不要为制造 findings 而要求改写已经满足需求的代码。

## 3. 验证证据

读取实际命令结果，必要时运行范围内检查；仅有“应该通过”或旧版本结果不算证据。
每条必需检查记录命令、结果、当前版本适用性和限制。无法运行时说明原因并保持未验证。
权限或环境限制不能伪装为成功；缺少关键验证时 Verdict 为 `incomplete`。
测试通过不能替代设计与代码审阅；发现影响代码的新修改后旧 review 结论失效。

## 4. 输出契约

仅审阅请求在答复中输出结果。完整开发任务或已授权写回时，在同一设计的 Review / Fix 中记录结果。
优先列出可行动问题：

```text
Findings
- ID / P0-P2 / blocking 或 non-blocking / 文件:行
  触发条件 → 当前行为 → 用户或系统影响；证据；建议的最小修复。

Design drift
- 差异、原因、是否仍满足 AC；实际文件范围与预算对照。

Simplification opportunities
- 可以移除的具体结构与理由，或“未发现有依据的简化项”。

Verdict
- pass | needs-fix | incomplete
- 已覆盖范围、验证证据、必要修复状态、剩余限制。
```

P0 表示严重正确性/安全/数据问题；P1 表示应当在本次交付前修复的问题；P2 通常为后续改进。
严重性与是否阻塞分别说明：即使标 P2，若违反必要验收也必须阻塞；不要靠降低级别绕过 G3。
无问题时写“在上述范围内未发现架构问题”，不评分，也不声称证明不存在任何 bug。

## 5. Fix → 复验 → 复审

完整开发任务修复 blocking findings，新增或调整能复现问题的必要测试，再运行受影响检查。
复读新 diff，确认没有回归或新的设计偏差；更新 finding 状态与证据，不擦除原来的原因。
对重复失败查根因；若依赖外部条件、授权或未知产品决策则报告阻塞，不无限重试或伪报完成。
非阻塞建议留下理由与后续项即可。仅在 AC 满足、必要验证通过、必要修复关闭且 review 覆盖
当前代码时，更新为 `done`。发布、合并和部署按任务既有授权单独处理。

可用独立子代理时，提供原始需求、设计、基线和完整文件范围，让其自行找问题；不要先告诉它
期待的结论。未实际使用独立子代理时明确是自审。
