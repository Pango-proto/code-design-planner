# 安装、全局规则与可选协作

本文件说明 `code-design-planner` 如何使用已经可用的能力。五阶段、三门禁、规模分级、diff budget 和审查要求以 [SKILL.md](../SKILL.md) 为准，不在这里维护第二份流程。

## 一份全局 skill，项目保留领域知识

推荐全局只安装一份 `code-design-planner`，并在更新时维护这一份。当前官方文档列出的用户级目录为 `~/.agents/skills/`；因此安装目标为 `~/.agents/skills/code-design-planner/SKILL.md`。开发这份 skill 的仓库可作为唯一源，通过受支持的目录符号链接接入全局技能目录；也可使用受控安装程序更新唯一安装副本。[官方：Build skills](https://learn.chatgpt.com/docs/build-skills)

全局 `$CODEX_HOME/AGENTS.md`（默认 `~/.codex/AGENTS.md`）只保留简短触发规则，指向这个 skill，不复制完整流程。项目 `AGENTS.md` 只补充领域概念、架构约束、测试命令、关键风险和项目特有验收标准；按任务规模按需维护 `docs/designs/`。不要为每个项目复制通用 skill 或通用开发流程。

Codex 从全局说明开始，再读取项目根到当前目录路径上的说明。同一目录优先采用 `AGENTS.override.md`，再采用 `AGENTS.md`；更深目录的说明可覆盖上层说明。因此应核对实际加载的指令来源，不要认为编辑了任意位置的文件就已全局生效。[官方：AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

仅在团队需要仓库自带、固定版本的 skill 时，才考虑项目级 `.agents/skills/code-design-planner/`。这是可选分发方式，不是默认要求。避免同时安装同名的全局与项目副本；Codex 不会自动合并它们。当前会话可能仍展示既有的 `~/.codex/skills/` 路径，这不能替代对目标客户端实际发现结果的验证。[官方：Build skills](https://learn.chatgpt.com/docs/build-skills)

安装后核对技能选择器或已加载技能列表；若未出现，按官方指引重启客户端。全局指令的加载也需要在新运行或新会话中验证。安装、启用与流程已经执行是不同事实，不能用其中一个代替另一个。

## 可选能力路由

先使用当前环境已经可用且符合任务范围的能力。仅按需阅读其 skill；不要为了运行本流程预先加载所有 skill、安装所有推荐插件，或要求每个项目使用同一技术栈。

| 能力 | 适用位置与边界 | 不可用时的处理 |
| --- | --- | --- |
| `project-file-governance` | 多阶段工作、文件治理、归档；保持设计记录和交付物有唯一位置 | 遵循项目既有目录规则，更新现有设计文件，不额外生成平行版本或整套治理目录 |
| `openai-docs` | 涉及 Codex、OpenAI API 或产品行为时核实官方约束 | 使用可访问的官方文档；无法核实的结论标为待验证，不凭记忆声称接口或命令存在 |
| `skill-creator` | 修改、验证本 skill 或创建其他 skill | 手工检查元数据、引用、触发条件和代表性使用场景；普通应用功能开发不需要调用它 |
| `skill-installer` | 用户要求安装或更新 skill 时 | 保留可安装的源文件和准确说明；不把安装其他 skill 设为核心开发的前置条件 |
| `visualize` | 复杂交互、状态变化、架构方案需要可交互说明时 | 在设计中使用简洁文字、表格或 Mermaid；图示不能代替验收条件 |
| `imagegen` | 需要位图、插画、产品视觉素材时 | 使用已有授权素材或明确标注的占位图，继续实现可独立推进的部分；不伪称已生成最终素材 |
| `sites:sites-building`、`sites:sites-hosting` | 用户明确使用 Sites，或任务符合该 skill 的建站与托管范围时 | 按当前仓库已有框架、构建与部署方式工作；普通 Web 项目不因此迁移到 Sites |
| 浏览器或原生 UI 工具 | 前端用户路径、响应式布局、可访问性及视觉验收 | 优先使用项目已有浏览器测试；若只能完成代码检查，明确保留未验证的交互或视觉项 |
| GitHub 工具、`git`、项目 CI | 获取变更、检查结果与 PR；仅在授权范围内提交或发布 | 本地 `git diff`、测试和审查仍可完成；远端状态无法读取时不声称 CI 已通过 |
| 文档、PDF、表格、演示 skill | 用户实际要求对应格式的交付物时 | 使用任务已约定且可支持的格式；不要把代码设计文档默认转换成多种格式 |
| `pages` | 用户明确要求把内容保存或维护到 Page/Space 时 | 继续维护项目中的设计记录；打开了一个 Page 不等于授权写入 |
| Figma、Linear 等外部服务插件 | 已连接且任务需要读取其设计或需求来源时 | 使用用户提供或仓库已有的材料；缺少的必要信息写为具体待决项，不默认安装或连接账户 |

Skill 提供流程；连接器或 MCP 提供受控的数据和动作。核心的需求分析、设计、实现、测试、diff 与审查可以只用仓库文件和已有工具完成，无需新增 MCP 服务。[官方：Build plugin skills](https://developers.openai.com/plugins/build/skills)

## 独立审查与降级

当规模或风险要求独立审查时，优先将设计、明确的变更范围、diff、验收条件和验证证据交给独立 reviewer。若当前运行环境支持子代理，可分派只读审查；也可使用团队已有的独立人工或 PR 审查。不要为了获得 reviewer 自动创建用户聊天、给其他聊天发消息或向外部服务发送代码。

独立 reviewer 应自行检视代码和证据，不能仅复述实现者的总结。修复完成后，复核修复涉及的范围；显著新增变更应重新经过相应门禁。明确记录 reviewer 来源和仍未验证的内容。

若没有独立 reviewer，可继续设计、实现、测试和自查，并形成可供审查的结果。自查必须标明为自查，不能改名为独立审查；适用级别要求独立审查时，该门禁保持待完成。缺少一个可选插件不等于缺少所有审查途径。

## 指令约束与机械检查的边界

Skill 通过显式引用或描述匹配启用。只有安装文件，不能保证所有功能开发都会自动执行流程。简短全局 AGENTS 触发规则提高一致性，实际执行仍需设计、测试及审查证据。[官方：Build skills](https://learn.chatgpt.com/docs/build-skills)

`$code-design-planner --review` 是本 skill 的模式选择约定：在提示词中进入 Reviewer Mode。它不是已存在的终端可执行程序，也不是官方 Codex CLI 参数。

需要硬性合并门禁的团队，可使用既有 CI 和仓库保护设置检查机器可判断的条件，例如：该规模是否需要设计文件、必要段落是否存在、必需测试是否通过、变更规模是否超过约定 budget。此类检查只能证明被检查的条件，不能证明需求被正确理解、设计合理或独立审查已经实质完成。

五阶段三门禁以任务规模和证据为准，不额外要求每关都等待用户确认。已授权且可逆的工作持续推进；需求存在不可替代的歧义、必要权限缺失，或操作需要新的授权时，才提出具体问题。不得把“某工具不可用”“测试未运行”或“review 尚未完成”改写为通过。
