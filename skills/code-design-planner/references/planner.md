# Planner Mode

目标是在写业务代码之前，把需求变成可实现、可验证、范围明确的设计。

## 1. 需求和代码事实

先读取适用的 `AGENTS.md`、已有设计、相关入口和调用方、测试与项目命令。
查看工作区状态，区分当前任务改动与用户原有改动。不要仅根据文件名推断架构。
记录原始目标、非目标、约束与假设，用 AC-01 等编号列出可观察的验收条件。
每条验收说明输入 / 操作及预期结果，覆盖重要失败路径。

对不影响核心决策的缺失信息采用最小假设并显式记录。缺失信息会改变授权、外部副作用、
数据所有权或核心验收时先询问；等待期间继续无依赖分析。别把实现细节反复变成用户选择题。

## 2. 最小可行设计

按 [设计模板](../assets/design-template.md) 在项目中创建或更新唯一设计文件。
文件名描述功能，不加 final / new / v2 等状态后缀；版本交给 Git。

说明这些变化为何必要：

- 当前职责与调用链；新职责放在哪里，哪些模块保持边界，依赖指向谁。
- 公共接口、输入输出、错误约定、调用权限；对已有调用方的兼容性。
- 数据从 UI / 调用入口经过业务逻辑到存储或外部服务的路径；状态和副作用由谁拥有。
- 替代方案及取舍；能否直接复用现有约定，用更少的概念满足需求。
- 预计新增、修改、删除文件；测试与文档同样计入范围；避免顺带重构。

不必为每个功能画图。关系或状态难以用短文字解释时，用 Mermaid 或可用可视化工具。
不要把“未来可能用到”当作新抽象的唯一理由。

## 3. 全栈检查按实际涉及层选择

| 层 | 设计需要回答的具体问题 |
|---|---|
| 前端 | loading / empty / success / error 的行为；可访问性、表单校验、权限显示、响应式与重复提交 |
| API / 业务 | 契约、服务端校验、认证授权、错误映射、重试 / 幂等需求、并发和副作用边界 |
| 数据 | 模型与约束、事务、一致性、迁移与旧数据、向前/向后兼容、必要的回滚方式 |
| 外部服务 / 运行 | 超时与失败处理、配置与凭据来源、日志/监控、部署顺序、必要的灰度或回滚 |

只检查受影响层；不涉及的层给一句 N/A 理由。不要为简单工具新增服务、数据库或基础设施。
安全相关设计跟着实际数据、信任边界和故障场景走，不输出与本次变更无关的通用检查清单。

## 4. 验证计划

将每个 AC 对应到已有或必要的新测试；标出集成契约、关键用户路径和失败路径的验证方式。
从仓库配置读取真实测试 / lint / typecheck / build 命令，不编造命令。
区分“计划运行”与“已运行”，注明需要的环境、数据与外部依赖。
预先定义哪些检查必需，哪些因本次范围不适用；不得为跳过失败检查而事后降级。

## 5. G2 与交接

设计足够具体、阻塞疑问关闭、范围属于授权时，标记 `designed`。
仅设计请求到此结束；完整开发请求由主代理继续实现并将状态更新为 `implementing`。
明确要求人工批准时保留 `proposed` 并交付设计，不能把沉默或时间流逝当作批准。
重大任务尽量让独立 reviewer 在实现前读需求与设计，避免只验证自己原有结论。

发现设计假设错误时，先停止依赖该假设的修改，记录原因与新的取舍，更新设计后继续。
保留原验收含义；不能通过改写需求来掩盖实现不符合需求。
