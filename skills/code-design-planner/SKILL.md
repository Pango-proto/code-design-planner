# Code Design Planner

让功能修改沿着可追溯的闭环推进：

```text
User Requirement → Requirement Analysis → Planner Mode
→ docs/designs/<feature>.md → Implementation → Tests
→ git diff → Reviewer Mode → Fix → 复验 / 复审 → Done
```

## 分层与范围

- 全局维护一份本技能与通用流程。项目 `AGENTS.md` 维护技术栈、目录、领域规则、架构约束和验证命令。
- 先读取实际生效的项目指令与相关代码。保留已有目录和工具，不为使用本技能安装插件或改造项目布局。
- 默认一个功能对应一份 `docs/designs/<feature>.md`，持续原地更新。项目已有设计位置时沿用并记录路径。
- 用户仅要求设计时只交付设计；仅要求 review 时只审阅。完整开发请求由主代理在各模式间推进。
- `--review`、`--plan`、`--full` 是写在技能调用消息中的模式约定，不是 shell 命令或 Codex CLI 参数。

## 模式选择

| 请求 | 行为 |
|---|---|
| 新功能、行为修复、重构，或 `--plan` | 先 Planner；`--plan` 表示仅设计 |
| `--review`、审查设计一致性、审查已有变更 | Reviewer；默认只读，结果在答复中报告 |
| `--full` 或“按需求实现并完成验证” | Planner → 主代理实现与验证 → Reviewer → 已授权修复 → 复验 / 复审 |
| 继续实现 | 先读已有设计、当前 diff 和验证状态；不从聊天记忆推断完成 |

### Planner Mode

实现前读取 [Planner 指导](references/planner.md)。明确目标、验收条件、当前系统、职责与边界、
依赖方向、契约、数据流、错误处理、测试方案、预计变更文件和取舍。
使用 [设计模板](assets/design-template.md)，删除不适用部分并注明理由，不写架构论文。
Planner 阶段不改业务代码；达到 G2 后将设计交给实现阶段。完整开发请求无需因此结束对话。

### Reviewer Mode

审查时读取 [Reviewer 指导](references/reviewer.md)。输入为原需求、设计、真实代码与完整变更范围、
验证证据。不假设设计或实现天然正确。不把未运行的测试、缺失的基线或遗漏的文件算作通过。
输出 Findings、Design drift、Simplification opportunities 和 Verdict，指出具体证据与影响。
已授权的完整开发中修复必要问题，重新验证受影响路径，再复审最新变更。

## 五阶段与三道门禁

| 阶段 | 必须留下的证据 / 转换条件 |
|---|---|
| Requirement / G1 | 目标、非目标、可观察的验收条件、约束、已知假设；没有阻碍设计的未知信息 |
| Design / G2 | 实现前可读取的设计、测试计划和变更预算；设计可实施且属于现有授权范围 |
| Implementation | 按设计实现；假设失效或范围增加时先更新设计与原因 |
| Verification | 实际运行的相关测试及适用的 lint / typecheck / build；记录失败、未执行和原因 |
| Review / G3 | 最新 diff 已审阅，验收和必要修复已关闭，相关复验通过，才可 Done |

G2 不默认要求用户逐次批准。用户要求“先设计等确认”、项目明确要求人工批准，或行动超出
现有授权范围时，交付具体设计后等待。G3 表示完成开发检查，不自动授予 merge / deploy 权限。
信息不全时先推进独立可做的工作；对会影响授权、数据安全或核心产品行为的选择不得静默猜测。

## 按风险控制篇幅

- **Trivial**：不改变行为的拼写、文案或格式修正。可用聊天里的简短需求与验证记录，无需创建设计目录；
  仍检查 diff，运行必要检查。不能仅凭“单行”“CSS”“配置”判定 trivial。
- **Normal**：一般功能、行为修复、新依赖、接口或数据变化。完整闭环，短设计即可。
- **Large**：跨系统、权限、支付、重要数据迁移或大规模重构。增加必要调研、兼容与回滚设计；
  有可用子代理时优先独立设计检查及最终审阅。没有子代理时以独立审阅步骤继续，不声称独立 agent 已审。

## 变更与完成纪律

1. 设计列出预计新增、修改、删除的文件或模块，并解释范围。预算是范围预警，不是机械行数限额。
2. 出现未预计的核心模块、外部服务、数据迁移或明显范围增长时先解释并修订设计；超出授权才请求决定。
3. 不以 SRP/OCP/DIP 等缩写代替论证，不为符合模式而引入接口、继承、工厂或事件总线。
4. 测试应证明验收与故障行为；不为可逆低影响改动添加仅复刻实现的测试。使用项目已有测试工具。
5. 有必要修复未完成、关键验收无法验证或 review 范围不明时，保持 `needs-fix` / `blocked`，不能写 Done。
   非阻塞建议可记录为后续项，不为关闭它们无限扩大本次范围。
6. 完整开发任务在同一设计中记录测试、review 和 fix；仅审阅时先在答复报告，只有授权写回才更新文件。
   不创建每轮会话副本，不覆盖用户无关改动。

按需参考 [技能与插件协作](references/integrations.md)。本技能、全局指令与 CI 的检查能力不同：
指令规定开发行为，自动校验只能证明其实际检查过的内容，不能证明设计正确或语义评审已发生。
